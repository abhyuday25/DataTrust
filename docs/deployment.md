# Deployment

`backend/Dockerfile` and `frontend/Dockerfile` build separate services. `docker compose up --build` uses a host Ollama instance at `host.docker.internal:11434` by default. Set `OLLAMA_DOCKER_BASE_URL` if the server has another address. Alternatively start the optional `ollama` profile with `docker compose --profile ollama up --build` and set `OLLAMA_DOCKER_BASE_URL=http://ollama:11434`; install the chosen models explicitly with `ollama pull` on the host or `docker compose exec ollama ollama pull <model>` in the container. The app never downloads models during startup. CPU-only Ollama is possible but slower.

Compose bind-mounts `./storage` for DuckDB, query history, cache, conversations, auth metadata and FAISS; `./data` holds uploaded files. The optional Ollama service uses the named `ollama_models` volume. Back up DuckDB and uploaded files together. `GET /api/health` is process liveness; `GET /api/readiness` checks configured Ollama models. A missing FAISS index is rebuilt when needed.

For production set `APP_ENV=production`, `AUTH_ENABLED=true`, `ADMIN_EMAIL`, and a strong `ADMIN_PASSWORD` via deployment secrets. Configure CORS for the deployed origin and put TLS and rate limiting at the ingress. Passwords and bearer tokens must never be baked into images or committed. The current DuckDB and in-process metrics design is suited to a single backend process; multi-replica deployment needs a shared transactional metadata store and distributed metrics. Docker/Compose execution requires Docker on the host and was not available in the development environment used for this implementation.
